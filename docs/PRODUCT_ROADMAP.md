# EvidenceGraph 产品路线图（精简版）

制定日期：2026-09-05；按新的产品范围修订：2026-09-16。

本文件是工作计划，不代表功能已经实现。阶段状态只根据实际验收记录更新；
写下路线图不构成部署、购买服务或一次性实现所有阶段的授权。

## 1. 一句话产品

上传 AI 研究论文 PDF，生成一张能点回原文的证据图谱；上传多篇时，
找出有依据的跨论文联系；提问时给出引用，并高亮图谱中真正支撑回答的部分。

核心路径：

1. 上传一篇 PDF → 等待处理 → 查看图谱 → 点击节点或关系 → 看原文片段和 PDF 页。
2. 加入第二篇 PDF → 查看各自图谱及跨论文联系 → 区分已核实关系与候选关系。
3. 对选中论文提问 → 查看带引用的回答 → 图谱高亮对应证据 → 点击返回原文。

图谱不是把段落随意画成“知识地图”。每个重要节点和关系都要记录来自哪篇
PDF、哪一页、哪段文字，以及抽取方式和状态。来源可定位不等于关系语义正确；
候选推断不能画成已核实事实。

## 2. 第一版范围和边界

- 只面向文字可提取的英文 AI 研究论文 PDF；允许中文提问和回答。
- 从单篇开始，多篇先支持选中 2–3 篇；体积、页数和性能限制由阶段 0 实测确定。
- 核心界面只有上传与处理状态、图谱、PDF/证据详情、提问区及必要的文档筛选。
- 最小图谱 schema 从论文、方法、数据集、实验/结果、主张、证据及少数有类型的关系起步；
  阶段 0 用真实样本收紧字段，不为“图很丰富”而抽取不可靠信息。
- 原文、解析结果、图节点/关系和问答引用使用稳定标识；重试、重建与删除后不能
  留下指向错误版本 PDF 的证据。

第一版暂不做：通用文档平台、完整论文库/专题管理、自动综述、论文优劣排名、
研究笔记、复杂图推理、多 Agent、批量扫描件 OCR、公开自由上传和本地大模型部署。
跨论文“联系”不等于可直接比较实验结果；指标、数据划分或条件不一致时，
不得自动得出优劣结论。

用户体验：上传论文，看到真实处理状态；图谱上的重要节点和连线都能点回原文。

- 先复用现有 FastAPI 和 Streamlit 形成完整流程，不为这一步重写前端。
- 使用 Docling 解析 PDF，保留标题、段落、表格及可获得的页码/位置；
  对损坏、加密、无文本或不支持的文件给出明确错误。
- 抽取固定 schema 的节点和有类型的关系，使用 Pydantic 校验输出；
  缺失字段保持缺失，坏模型输出不能变成确定事实。
- 原始 PDF、解析产物、图数据和处理任务可持久保存；处理失败、重试、重启
  和重复提交不能产生重复图或永久“处理中”的任务。
- 每个可展示关系关联证据 ID；点击关系时展示原文、页码和定位粒度。
  没有可靠证据的关系不展示为确定事实。
- 图谱支持按类型筛选、局部展开和规模限制；解析或抽取失败时仍可查看
  已成功保存的 PDF 与错误状态。删除论文时清理其图和来源引用。

验收：样本 PDF 上传后有可交互图；人工逐条核对样本关系及回跳；
坏文件、坏模型输出、重试、重建和删除有测试；记录误抽取案例与处理耗时。

## 6. 阶段 2：多篇 PDF → 保守的跨论文联系

用户体验：选择 2–3 篇论文，看到每篇自己的图，以及它们之间的关系。

- 先做可解释的联系：明确引用另一篇、使用同一已消歧数据集、
  或讨论同一已消歧方法；保存每篇论文各自的证据。
- 名称相同不自动合并实体。仅靠相似文本得到的联系标记为“候选”，
  在图中与已核实关系视觉区分，并允许查看为什么被推荐。
- 保留单篇图与跨篇连线的区别；可按论文、关系类型和状态筛选。
- 不把不同数据集版本、划分、任务、指标或实验条件下的结果自动排名。
- 删除或重建一篇论文时，只撤销它贡献的联系，不误删另一篇的独立节点。

验收：人工标注的相同/不同实体案例可复核；候选联系不会伪装成事实；
跨篇连线能看到双方依据；删除与重建不留下悬空或错误连接。

## 7. 阶段 3：问答 → 引用与图谱高亮

用户体验：对选中论文提问，看到回答的原文依据，同时看见图中对应部分亮起。

- 先在所选 PDF 的文本片段中检索，再生成带证据 ID 的回答；
  限定检索范围，不只在提示词里说“仅看这些论文”。
- 校验引用 ID 必须属于所选文档和当前版本；无足够证据时明确说不知道。
  引用有效仍不代表引用语义上足以支持结论，保留人工核查样例。
- 由证据 ID 映射到图节点/关系 ID 再高亮；一条引用没有图映射时，
  照常展示引用，不强行高亮无关节点。
- 点击回答引用或高亮部分，回到 PDF 原文；精确坐标不可用时退化为页码
  和片段定位，并说明粒度。
- 先做简单可测的检索基线。只有评测显示需要时，才引入 Qdrant、
  混合检索或重排序。图谱可浏览、可高亮，不意味着必须参与答案检索；
  图检索须另有收益证据再决定是否启用。

验收：事实、无答案、坏模型输出、API 超时和跨文档串证据有测试；
人工核对样本回答的引用支持性与高亮准确性；记录失败例、耗时和模型用量。

## 8. 阶段 4：受控演示与部署

用户体验：在本地或经确认的服务器上，稳定走通上传、图谱、跨篇联系和问答。

- 先做只读预置论文演示；是否开放私人上传，取决于身份认证、
  文档所有权隔离、下载/查询权限、文件与模型调用限额的验收。
- 根据图谱/PDF 联动的实际界面需求再决定是否迁移 React/Next.js；
  领域逻辑留在后端，不为了换前端重复实现抽取与引用规则。
- 图数据先采用满足前几阶段查询的简单持久表示；只有关系查询和规模
  测试表明必要时才引入 Neo4j。部署清单不预先强制纳入 Qdrant 或 Neo4j。
- 明确第三方模型的数据流向、保留期限和删除方式；处理 PDF 与模型输出
  时限制资源消耗并防范提示注入。
- 服务器、域名、模型费用及公开发布由用户另行确认；配置 HTTPS、
  备份恢复、健康检查、日志脱敏、费用上限和回滚流程。

验收：干净环境可按文档启动，预置样本完整走通；重启、备份恢复、
权限隔离和超时行为经过验证。未通过上传安全验收时仅发布只读演示。

## 9. 后续候选，不属于本次 MVP

按真实使用和评测结果再决定：更广文档类型、实验条件对照表、
图辅助检索、研究笔记与导出、结论核验、本地模型服务或更专业的前端。
不因为这些技术在设想架构里出现，就提前加入依赖或承诺上线。

## 10. 每阶段交付与验证

每个阶段都记录：完成与未完成项、用户操作路径、数据流和设计取舍、
新增测试及实际结果、人工核查样例、已知失败与资源消耗、下一阶段风险。
修改行为后运行相关测试；里程碑运行完整测试、lint 和类型检查：

~~~bash
uv run pytest
uv run ruff check .
uv run pyrefly check
~~~

以上是默认验证命令，不表示本次文档修订已经运行过它们。
面试准备重点：为什么先定义证据 ID、来源定位与语义正确有何区别、
候选关系为何不能当事实，以及为何图谱高亮不要求先做图检索。
